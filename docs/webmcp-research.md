WebMCP API research, checked 28 September 2026.

The current draft places the API on `document.modelContext`. `registerTool(tool, options)` returns a promise. A tool has a name, description, JSON Schema input, an `execute` callback, and optional annotations. Names must use 1–128 ASCII letters, digits, underscores, hyphens, or dots. Registration rejects duplicate names. The API requires a secure context. [WebMCP draft](https://webmachinelearning.github.io/webmcp/)

The callback contract is `execute(inputObject, { signal }) => Promise<any>`. The draft serializes its resolved value as JSON before returning it to the caller; a rejected callback fails the call. Return a JSON-safe object, without DOM objects, functions, cycles, or `BigInt`. An MCP-style `content` array can be part of that object, but the draft does not require that wrapper. For expected input errors, a small result with an error code and a clear message preserves more detail than relying on browser error text. This last point is an application design choice. [Execution steps](https://webmachinelearning.github.io/webmcp/#imperative-execute-steps)

Current registration cleanup uses an `AbortController`: pass its signal to `registerTool`, then abort it when the owning view unmounts. This registration signal controls availability. The signal passed to `execute` controls that call. Removing a tool does not cancel a call whose callback has started. Chrome documents that separation from version 153. [Chrome imperative API](https://developer.chrome.com/docs/ai/webmcp/imperative-api#unregister-tools)

In-page agents discover tools with `await document.modelContext.getTools()`, then call `executeTool(discoveredTool, inputObject)`. `toolchange` reports changes to the list. Chrome deprecated JSON-string arguments to `executeTool` in version 155. Browser agents discover registered tools through their own browser integration; a page need not expose a custom global to enable them. [Chrome discovery and execution](https://developer.chrome.com/docs/ai/webmcp/imperative-api#discover-tools)

The older proposal used `navigator.modelContext.registerTool(tool)` and `unregisterTool(name)`. Its examples return both strings and `{ content: [{ type: "text", text: "..." }] }`. Its `provideContext` call replaces the whole tool set, which makes it a poor fit for a feature that owns only its own tools. Treat these as compatibility details, not the current API. [Earlier WebMCP proposal](https://webmachinelearning.github.io/webmcp/docs/proposal.html#modelcontext)

For this editor, prefer a callable `document.modelContext.registerTool`, then fall back to `navigator.modelContext.registerTool`. Pass a registration signal and handle both a promise and an older void return. On cleanup, abort the signal and call `unregisterTool` only when that method exists, for names this instance successfully registered. Keep registration errors visible in readiness state. These are proposed adapter rules based on the two API versions above; presence alone does not prove that registration succeeded.

WebMCP remains a proposed standard. Chrome offers an origin trial and the local `chrome://flags/#enable-webmcp-testing` flag. Its docs recommend the Model Context Tool Inspector extension for listing and calling tools. A client must visit the page to discover its live tools. Keep the editor usable when the API is absent and link the readiness label to setup and usage instructions. [Chrome WebMCP overview](https://developer.chrome.com/docs/ai/webmcp)

Use one clear action per tool, typed parameters, and runtime validation with useful errors. Reuse the editor's actions so tools and buttons update the same state. Resolve a completed edit only after the edit reaches that state; distinguish starting playback or rendering from finishing it. Avoid overlapping tools and unnecessary re-registration. These choices follow Chrome's guidance on clear names, strict code validation, and keeping the UI in sync. [WebMCP best practices](https://developer.chrome.com/docs/ai/webmcp/best-practices)

Set `readOnlyHint: true` only for calls that change no state. Use `untrustedContentHint: true` when returning user-written CSD text, file names, or external content. Reserve `consequentialHint` for significant or irreversible actions. Keep tool descriptions and results short; page long source reads instead of silently cutting them off. Keep the default origin access unless a named integration needs more. Hints describe behavior; they do not replace the editor's access checks or input validation. [WebMCP tool security](https://developer.chrome.com/docs/ai/webmcp/secure-tools)

The declarative API turns HTML forms with `toolname` and `tooldescription` into tools. Fields define parameters; `toolautosubmit` opts into submission. This suits forms. The imperative API is the natural fit for CodeMirror edits, tab changes, playback, and rendering, because those actions already use JavaScript application state. [Chrome declarative API](https://developer.chrome.com/docs/ai/webmcp/declarative-api)
